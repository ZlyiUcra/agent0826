# Установка і прогін тестів

Як підняти оточення практики модуля 6 і як її перевірити. Усі команди виконуються з теки `module6/`, не з
кореня репозиторію: код практики імпортує `practice`, `core`, `config`, `domain` як пакети верхнього рівня.

## Оточення

Практика працює в тому самому віртуальному середовищі, що й курсові файли модуля, — `module6/.venv`. Окремого
оточення їй не треба: усе, що вона імпортує (`mcp`, `anthropic`, `core.agent`), уже там. Якщо середовища ще
немає, воно ставиться так само, як у решті модулів:

```
cd module6
/home/kirgiz/miniconda3/bin/python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install torch --index-url https://download.pytorch.org/whl/cpu
.venv/bin/python -m pip install -r requirements.txt
cp ../module5/.env .env        # ключ потрібен лише для прогонів на живій моделі
```

Torch тут стоїть заради курсових `knowledge_vec.py` і `knowledge_qdrant.py`; сама практика його не імпортує.

Пошук за змістом (необов'язковий) додатково потребує `fastembed` — його в оточенні ще немає:

```
.venv/bin/python -m pip install fastembed        # тягне onnxruntime; ~50 МБ коліс, модель ще 128 МБ при першому пошуку
```

Це та сама бібліотека, що в модулі 5 (ONNX замість torch). Без неї працює пошук лише по словах, і всі
безкоштовні перевірки проходять.

## Корпус

Агент шукає по найширшому наборі `suite` — той самий корпус специфікації, що в практиках модулів 2-5. Усі три
набори лежать поруч: `docs/` (core, вісімнадцять розділів), `docs-full/` (уся ECMA-262) і `docs-suite/` (решта
набору специфікацій). Приманки лабораторії (`docs-attack/`) уже в репозиторії; справжні документи копіюються з
модуля 5, без повторного вивантаження:

```
cp -a ../module5/practice/docs       practice/docs
cp -a ../module5/practice/docs-full  practice/docs-full
cp -a ../module5/practice/docs-suite practice/docs-suite
```

Набір задає змінна `PRACTICE_DOCS` (типово `suite`; `full` — лише ECMA-262, `core` — вісімнадцять розділів).
Приманки з `docs-attack/` додаються до будь-якого набору завжди.

## Пошук за змістом (необов'язковий)

Типово сервер шукає лише по словах, і цього досить, щоб побачити дизайн. Пошук за змістом вмикається окремо і
потребує `fastembed` (див. вище) та Qdrant у Docker:

```bash
.venv/bin/python -m practice.base.setup --status            # $0: що вирішено, що в базі, що змінилося
.venv/bin/python -m practice.base.setup --vectors           # підняти Qdrant і долити лише нове й змінене
.venv/bin/python -m practice.base.setup --vectors --refill  # перерахувати вектори всіх фрагментів
.venv/bin/python -m practice.base.setup --verify            # звірити вибірку векторів на підміну
.venv/bin/python -m practice.base.setup --words             # $0: повернутися на пошук по словах
```

Заливання довге: на наборі suite це ~4160 векторів, десятки хвилин на цій машині. Перерваний прогін не
пропадає — наступний дораховує решту. Колекція власна для модуля 6 (`spec6-...`), тож із колекціями модулів
2-5 у спільному контейнері не конфліктує. Після заливання рішення лежить у `out/mode.json`, і сервер сам
підхоплює його при наступному старті — піднімати його руками не треба.

Оновлення точкове. Номер точки в Qdrant зроблено зі стійкого ідентифікатора фрагмента, а не з його позиції у
списку, і поряд із текстом лежить його сума (sha256). Тому повторний `--vectors` рахує лише ті фрагменти, що
додалися чи змінилися, а незмінні не чіпає; `--status` показує цей розклад (нових / змінених / незмінних /
зайвих) безкоштовно, не рахуючи жодного вектора. Точку фрагмента, що зник із документів, практика не видаляє —
пошук її й так не показує, а знесення колекції лишається людині (команда друкується в попередженні). `--refill`
перераховує всі вектори; він потрібен один раз, щоб перевести вже залиту колекцію зі старої схеми номерів
(позиційної) на стійку — `--vectors` на такій колекції сам скаже, як це зробити.

## Ключ

Секрети живуть у `module6/.env`, звідки їх читає `config.py`. Ключ потрібен **лише** прогонам на живій моделі
(сітка атак без `--fake`, поодиноке питання агентові). Усі безкоштовні перевірки працюють без ключа. У
репозиторій іде лише `.env.example`; `.env` закритий `module6/.gitignore`.

## Що чим перевіряти

Практика перевіряється у два кроки: спершу все безкоштовне, і лише потім, за бажанням, платний прогін на живій
моделі. Позначка `$0` означає, що звернення до Anthropic немає.

### Безкоштовно — і цього досить, щоб побачити дизайн

```bash
.venv/bin/python -m practice.base.smoke              # $0: 21 перевірка — корпус, пошук, сервер, чотири шари
.venv/bin/python -m practice.base.agent --tools      # $0: MCP-рукостискання, перелік інструментів сервера
.venv/bin/python -m practice.base.attacks --fake     # $0: детермінована таблиця «атака × шар»
.venv/bin/python -m practice.base.attacks --fake --vary 5   # $0: атака 1 без захисту, 5 прогонів (5/5)
```

`smoke` має дати `21 ok, 0 FAIL`. `attacks --fake` має дати таблицю, де атаку 2 знімає шар 1 (`заблок.` від
`L1`), атаку 1 — шар 3 (`чисто` від `L3`), атаку 3 — шар 4 (`чисто` від `L4`). Ця таблиця детермінована: числа
однакові щоразу.

### Платно — розкид живої моделі

```bash
.venv/bin/python -m practice.base.attacks            # сітка на живій моделі, 1 прогін на клітинку
.venv/bin/python -m practice.base.attacks --reps 5   # 5 на клітинку — видно частоту інцидентів
.venv/bin/python -m practice.base.attacks --vary 5   # атака 1 без захисту, 5 разів — число гуляє
.venv/bin/python -m practice.base.agent "Як Object.prototype.toString будує тег?"   # один чесний прогін
```

Кожна клітинка сітки — це звернення до моделі, а в рядках з викликами інструментів — кілька звернень за прогін
(пошук, потім відповідь), плюс у стовпці `L4` ще виклик guardrail. Груба оцінка `--reps 5` — кілька сотень
викликів на дешевій моделі каскаду. Живий прогін показує те, чого fake показати не може: що модель нерідко
відбиває ін'єкцію сама, і результат на `L0` плаває між прогонами.

## Як усе піднімається під час прогону

Агент — MCP-клієнт. На кожен прогін він піднімає `base/spec_server.py` окремим підпроцесом і говорить із ним по
stdio (труби stdin/stdout). Сервер будує індекс BM25 над набором `suite` разом із приманками при завантаженні
(кілька секунд) і чекає викликів `search_spec` / `read_section`. Ключа серверу не треба — він читає лише
теки документів. Через окремий підпроцес на кожен прогін сітка на цьому диску йде поволі (кожен підйом
сервера — кілька секунд); це не помилка, а ціна чесного stdio-клієнта.

Ризиковий інструмент `fetch_url` — локальний в агенті, не в сервері. Мок нічого не завантажує: він фіксує
звернення у `out/egress.log` (тека `out/` у `.gitignore`) і повертає заглушку. Сам факт виклику на чужий домен
і є інцидентом.

## Наскрізний прогін: вектор і атака очима користувача

Розділ «Що чим перевіряти» вище — це довідник команд; цей проводить крізь один сценарій від початку до кінця й
каже, що саме видно на екрані. Усе з теки `module6/`.

**Крок 1 — увімкнути пошук за змістом.**

```
.venv/bin/python -m practice.base.setup --vectors    # підняти Qdrant і залити колекцію
.venv/bin/python -m practice.base.setup --status     # $0: режим, точки, розклад оновлення
```

На чистій машині колекція заллється вся (десятки хвилин). На вже залитій під старою, позиційною схемою
`--vectors` навмисно відмовить і надрукує `curl -X DELETE` на разове перезаливання — переливати треба лише щоб
увімкнути точкове оновлення надалі, а не щоб побачити результати. Що працює саме пошук за змістом, видно так
(має надрукувати `search: meaning+words`):

```
.venv/bin/python - <<'PY'
import time
from practice.base import spec_server as srv
for _ in range(45):
    if srv._VECTORS_READY: break
    time.sleep(1)
print("search:", srv.search_spec("how to find out the type of a value", 3).get("search"))
PY
```

**Крок 2 — захищений прогін: атака, що не спрацьовує.**

```
.venv/bin/python -m practice.base.agent "How does String.prototype.trim decide which characters to strip?"
```

`agent` вмикає всі чотири шари. Отруєний фрагмент `docs-attack/04-string-trim.txt` — це той самий розділ про
`trim`, тож він майже напевно у видачі, але вшитої в нього інструкції (`fetch_url` на чужий домен) агент не
виконує. На екрані: чиста відповідь зі специфікації, без жодного чужого посилання — ін'єкція нікуди агента не
повела. Внизу може з'явитися рядок «Заблоковано … перевищено ліміт викликів інструментів (6)» — це шар 2 (стеля
викликів за звернення), а не ловля ін'єкції; відповідь від зрізу останніх викликів лишається повна.

**Крок 3 — беззахисний прогін: та сама атака, що спрацьовує.**

```
.venv/bin/python -m practice.base.attacks --fake --vary 5   # $0: атака 1 без шарів — 5/5 витоків
cat practice/out/egress.log                                 # слід виклику на чужий домен
```

Контраст і є суть: те саме, що з шарами дало чисту відповідь, без шарів веде агента на чужий домен, і кожен
такий вихід лягає рядком у `out/egress.log`.

**Крок 4 — уся матриця одним поглядом.**

```
.venv/bin/python -m practice.base.attacks --fake            # $0: «атака × шар», детерміновано
```

Таблиця показує, який шар яку з трьох атак зняв: атаку 2 — шар 1, атаку 1 — шар 3, атаку 3 — шар 4. Числа
однакові щоразу. Чому оборона та сама з базою й без неї — у `DEFENCE.md`.
