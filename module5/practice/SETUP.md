# Установка і розробка

Як підняти практику модуля 5 з нуля і як з нею працювати далі. Усі команди виконуються з теки `module5/`, не
з кореня репозиторію: скрипти імпортують `practice` як пакет верхнього рівня, а сам сервер додає корінь
модуля у `sys.path` сам, бо його запускає чужий клієнт зі своєї поточної теки.

Практика — це MCP-сервер над пошуком по специфікації ECMAScript. Що він робить і чому саме так — у
`README.md`; стан чекбоксів картки — у `CHECKLIST.md`; план, за яким усе робилося, — у `PLAN.md`. Тут лише
порядок дій.

## Що має бути на машині

- **Python 3.14** — ним зібране `module5/.venv`. Обов'язково.
- **Node не нижче 20.12** — тільки для MCP Inspector. На Node 18 Inspector не запускається взагалі: у
  `node:util` тих версій немає `styleText`, і він падає з `The requested module 'node:util' does not provide
  an export named 'styleText'`. Перевірити: `node -v`. Перемкнути: `nvm use 22`, а щоб назавжди —
  `nvm alias default 22`. Без Inspector усе інше працює.
- **Docker** — тільки для пошуку за змістом. Без нього сервер шукає по словах, і жодна перевірка від цього
  не провалюється.

## Швидкий старт

Якщо оточення вже зібране, підйом складається з однієї команди і трьох перевірок:

```
.venv/bin/python -m practice.base.setup                 # одне питання, і далі все саме
.venv/bin/python -m practice.base.smoke                 # 32 перевірки, ~15 с, $0
.venv/bin/python -m practice.base.check                 # діалог по протоколу, ~10 с, $0
.venv/bin/python -m practice.base.quality               # що дає пошук за змістом, ~30 с, $0
```

Сам сервер запускати не треба взагалі — його запускає клієнт, коли до нього звертається. Перевірити, у якому
стані все зараз, можна будь-коли:

```
.venv/bin/python -m practice.base.setup --status
```

## Оточення

У модуля власне віртуальне середовище — `module5/.venv`. Глобальним і середовищами сусідніх модулів він не
користується: модуль має підніматися сам по собі, не знаючи про сусідів.

```
cd module5
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r requirements.txt    # курсові залежності модуля
.venv/bin/python -m pip install fastembed              # лише для практики
```

`requirements.txt` — курсовий файл модуля, він ставить `anthropic`, `mcp`, `a2a-sdk` і решту, з чим працюють
заняття. Практиці з цього потрібен лише `mcp`; ключі Anthropic їй не потрібні взагалі.

`fastembed` — єдина залежність понад курсові, і потрібна вона лише тоді, коли вмикають пошук за змістом. Вона
тягне за собою `onnxruntime`, `tokenizers`, `huggingface_hub`, `numpy`, `pillow`, `requests`, `tqdm`, `loguru`
і `mmh3` — разом 178 МБ у `.venv`, з яких на `numpy` і `onnxruntime` припадає 137.

Без пошуку за змістом її можна не ставити зовсім. Імпорт лінивий і стоїть усередині функції, яка вантажить
модель, тож сервер доходить до нього лише тоді, коли Qdrant справді відповідає і в колекції є точки. Це
перевірено, а не задумано: із записаним рішенням «vectors», але недосяжною базою `fastembed` не потрапляє в
`sys.modules` узагалі, а сервер пише причину в stderr і шукає по словах.

Чому `fastembed`, а не `sentence-transformers`, якими та сама робота зроблена в модулі 4: `import
sentence_transformers` на цьому диску триває 120 секунд навіть на теплому кеші, бо тягне тисячі дрібних
файлів torch через 9p, а MCP-сервер, який дві хвилини мовчить, клієнт вважає мертвим. `fastembed` рахує ті
самі числа рушієм ONNX і імпортується за шість із половиною секунд.

## Ключ

Не потрібен. Сервер не звертається ні до Anthropic, ні в мережу: він читає теки `docs*/` і говорить із
Qdrant на `localhost`, коли той увімкнений. Жодна команда цієї практики грошей не коштує.

`module5/.env` існує і лежить у `.gitignore` разом із `.venv/` і `out/` — але серверу він не потрібен, і
`config.py` практика не імпортує.

## Один вибір: Docker із Qdrant чи ні

Це єдине рішення, яке за людину ухвалити не можна, тому воно ставиться питанням рівно один раз:

```
.venv/bin/python -m practice.base.setup
```

Питання перелічує все, що з'явиться на машині — контейнер `agent0826-qdrant`, іменований том, модель на
128 МБ, — і скільки триватиме рахунок саме зараз. Відповідь: `y` піднімає, `n` лишає пошук по словах, `q`
виходить, нічого не змінивши. Порожній рядок означає `n` — на це вказує велика літера в `[y/N/q]`.

Відповідь лягає у `practice/out/mode.json`, і більше це питання не ставиться нікому — зокрема й тому, хто
потім користується інструментами в Claude Code. Сервер цей файл лише читає.

Будь-яка інша відповідь не вгадується: приходить `Unclear answer` і прохання ввести одну з трьох літер.
Порожній рядок від друкарської помилки тут відрізняється навмисне — порожній рядок це вибір, названий у
питанні, а помилка вибором не є.

Без питань, для скриптів:

```
.venv/bin/python -m practice.base.setup --vectors      # з Qdrant
.venv/bin/python -m practice.base.setup --no-vectors   # лише пошук по словах
```

Відмова нічого не ламає: сервер працює по словах над тим самим набором документів, і поле `search` у кожній
відповіді каже, який спосіб відпрацював.

Після кожної з цих команд друкується звіт: що записано, у якому стані база, скільки підійматиметься сервер і
які команди йдуть далі. Той самий звіт у будь-який момент дає `--status`.

## Перше заливання векторів

Це найдовша частина підготовки, і робиться вона один раз. На цій машині — 0.635 с на фрагмент, тобто близько
сорока хвилин на всі 4162 (заміряно 29 серпня 2026 року; вісім потоків ONNX замість типового одного дали
0.635 с проти 0.719 с, тож упирається не в потоки).

Що з цього випливає для роботи:

- Заливання йде пачками по 128 і друкує поступ із залишковим часом. Перерваний прогін не пропадає: наступний
  запуск дораховує з того місця, де зупинився попередній.
- Перед дорахунком звіряються три наявні точки — перша, середня й остання. Якщо набір документів змінився не
  з кінця, а всередині, номери точок означають уже інші фрагменти, і дорахунок приписав би текст одного
  фрагмента до вектора іншого. У такому разі підготовка нічого не чіпає і каже зробити
  `--vectors --refill` — повний перерахунок.
- Модель довантажується сама при першому використанні і лягає в `~/.cache/huggingface`. Перший запуск через
  це довший за наступні.

## Вимкнути пошук за змістом

```
.venv/bin/python -m practice.base.setup --stop
```

Записує пошук по словах і зупиняє контейнер. Порядок саме такий, і він важливий: зупинити контейнер, не
змінивши рішення, — марна праця, бо сервер прочитає з файла «vectors» і підніме його назад при наступному ж
запуску, як і задумано.

Різниця між `--no-vectors` і `--stop`: перший лише записує рішення, і контейнер працює далі, просто ним ніхто
не користується; другий ще й зупиняє його. Дані в обох випадках лишаються на місці, і `--vectors` повертає
все за секунди, не перераховуючи жодного вектора.

Нічого не видаляється в жодному разі — ані колекція, ані том, ані контейнер. Том спільний з лабораторною
модуля 2, і команда практики не має права зносити чужі дані. Прибрати його може лише людина і лише руками:

```
docker rm agent0826-qdrant          # контейнер; том лишається
docker volume rm agent0826-qdrant   # і всі дані в ньому, включно з чужими колекціями
```

## Точки входу і що скільки коштує

Позначка `$0` тут стосується всього: жодна команда практики не звертається до моделей Anthropic.

- `practice.base.setup` — підготовка. `--status`, `--vectors`, `--no-vectors`, `--stop`, `--refill`. $0.
- `practice.base.smoke` — 32 перевірки повз протокол: пошук, обрізка, межі `k`, описи інструментів, поведінка
  без векторів. ~15 с, $0.
- `practice.base.check` — справжній stdio-клієнт: піднімає сервер підпроцесом, бере перелік інструментів,
  кличе обидва. ~10 с, $0.
- `practice.base.raw` — ті самі кадри JSON-RPC руками, без клієнтської бібліотеки. `--full` не обрізає.
  ~10 с, $0.
- `practice.base.quality` — замір: чи додає пошук за змістом те, чого не давав пошук по словах. `--show`
  друкує ще й знайдені розділи. ~30 с, $0.
- `practice/base/spec_mcp.py` — сам сервер. Руками не запускають: він мовчки чекає клієнта на stdio.
- `practice.challenges.suite_download --status` — чи не змінилося джерело під `docs-suite/`. Тринадцять
  звернень, нічого не записує, $0. Те саме для `docs-full/` робить `practice.challenges.spec_download
  --status`, але там дешево видно лише перелік розділів: tc39.es перезбирає видання на кожен злитий запит,
  тож вміст звіряє `--status --deep`, а це тридцять вісім звернень.
- `practice.challenges.suite_download --refresh <id>` — перечитати один документ, а не весь набір. Два PDF
  (ECMA-404 і ECMA-414) розбирає `pypdf`, якого серед залежностей цього модуля немає; поки сервери кажуть
  «не змінювався», він і не потрібен, а знадобиться — скрипт скаже про це словами.

## Підключення клієнтів

Claude Code — обидва шляхи абсолютні, бо клієнт запускає сервер зі своєї поточної теки:

```
claude mcp add ecma-spec -- \
  /mnt/c/Projects/fwdays/agent0826/module5/.venv/bin/python \
  /mnt/c/Projects/fwdays/agent0826/module5/practice/base/spec_mcp.py
claude mcp list
```

Після зміни набору документів або режиму пошуку сервер у клієнті треба перепідключити: `/mcp` → `ecma-spec` →
Reconnect. Процес у клієнта старий, і він і далі тримає той індекс, з яким запустився.

Inspector потребує Node не нижче 20.12 — у ранніх версіях немає `styleText` із `node:util`, і Inspector падає
з `The requested module 'node:util' does not provide an export named 'styleText'`:

```
source ~/.nvm/nvm.sh && nvm use 22
npx -y @modelcontextprotocol/inspector .venv/bin/python practice/base/spec_mcp.py
```

Якщо `npx` падає з «Cannot find native binding» — це відома вада npm, а не поломка сервера: `rm -rf
~/.npm/_npx` і повторити.

## Що працює і як це зупинити

Тут три різні речі з трьома різними життєвими циклами, і плутати їх не варто — команда, яка гасить одну, двох
інших не чіпає.

**Сам MCP-сервер** окремим життям не живе взагалі. Його запускає клієнт як свій підпроцес і вбиває разом із
собою: закрився Inspector — помер і сервер; скінчилася сесія Claude Code — те саме. Тому запускати його
руками не треба, і гасити теж. Якщо все-таки лишився сиротою:

```
pgrep -af spec_mcp.py     # подивитися, чи є
pkill -f spec_mcp.py      # прибрати
```

**Inspector** — процес переднього плану, і саме тому сторінка в браузері живе рівно стільки, скільки його
термінал. Ctrl+C, закритий термінал, вимкнений комп'ютер — і браузер одразу дає `ERR_CONNECTION_REFUSED`.
Токен у адресі теж не переживає перезапуску: щоразу друкується новий, і посилання зі старим не відкриється.

```
Ctrl+C                            у терміналі, де його запускали
pkill -f mcp-inspector            забутий або чужий процес, разом із його spec_mcp
ss -ltn | grep -E "6274|6275"     має бути порожньо
```

Порти 6274 (сторінка) і 6275 (пісочниця) Inspector займає на весь час роботи. Другий екземпляр на них не
підніметься, тож перед новим запуском варто впевнитися, що старого немає — забутий Inspector над курсовим
`tracking_mcp.py` виглядає точно так само, як свій, і тримає ті самі порти.

**Qdrant** — контейнер, і `pkill` до нього не має стосунку. Він зупиняється командою з розділу «Вимкнути пошук
за змістом» вище: `setup --stop`. Просто `docker stop agent0826-qdrant` теж зупинить, але сервер підніме його
назад при наступному запуску, бо в файлі рішення стоїть `vectors`, — тому команда практики спершу змінює
рішення і аж потім зупиняє.

Подивитися все разом:

```
pgrep -af "mcp-inspector|spec_mcp.py"
docker ps --filter name=agent0826-qdrant
.venv/bin/python -m practice.base.setup --status
```

## Змінні оточення

- `PRACTICE_DOCS` — `core` (вісімнадцять розділів навколо типу Object, 283 фрагменти), `full` (уся ECMA-262,
  2436) або `suite` (вона ж плюс ECMA-402, 404, 414 і десять вільних документів довкола 402, 4162). Типове
  значення `suite` стоїть у `practice/__init__.py` через `setdefault`, тож названий в оточенні набір лишається
  за власником.
- `PRACTICE_EMBED_MODEL` — `bge-small` (типово, 384 виміри) або `bge-base` (768). Ім'я моделі входить в ім'я
  колекції, тож перемикання не псує вже залитих векторів — воно веде в іншу колекцію, і ту доведеться залити
  окремо.
- `QDRANT_URL`, `QDRANT_CONTAINER`, `QDRANT_VOLUME`, `QDRANT_IMAGE`, `QDRANT_COLLECTION` — де шукати базу і
  якими іменами її піднімати. Типові збігаються з лабораторною модуля 2, щоб на машині не з'явилося другої
  бази з тими самими даними.

## Правила розробки

- Курсові файли модуля не змінюються: `core/`, `domain/`, `config.py`, `modules/`, `run.py`,
  `tracking_mcp.py`, `courier_server.py`. Усе нове живе в `practice/`.
- Інструментів рівно два. Третій не додається, навіть коли здається корисним: кожен новий опис модель читає
  перед кожним своїм рішенням.
- Код нічого не видаляє. Журнал `out/calls.log` тільки дописується, колекції й томи не чіпаються, записи
  прогонів у `out/` прибирає людина, якщо захоче.
- У stdout сервера не можна нічого, крім кадрів протоколу: будь-який `print` без `file=sys.stderr` ламає
  клієнтові розбір відповіді. Перша перевірка, яка це ловить, — `check.py`.
