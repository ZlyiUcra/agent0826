# Практика модуля 1 — агент з ланцюжком інструментів

## Узгоджена пропозиція

Домашня робота курсу до модуля 1: агент підтримки поштового оператора, який відповідає на запит клієнта,
що не закривається одним викликом API. Клієнт називає лише свій телефон, а не трек-номер, тому агент
мусить спершу знайти відправлення за телефоном і лише потім, за отриманими номерами, дізнатися статуси —
результат першого інструмента є єдиним джерелом аргументів другого. Агент не вигадує факти: коли пошук
нічого не знаходить, клієнт отримує чесне «не знайдено», а грошові суми у відповіді звіряються з тим, що
реально повернули інструменти. Витрати обмежені: вичерпаний бюджет зупиняє наступний запуск із чесним
поясненням причини. Робота живе всередині module1/ як окрема тека практики, курсовий матеріал не
змінюється; поведінка доводиться реальними прогонами у README — одним вдалим і чотирма зламаними — і
тестами, що ганяють логіку без мережі.

## Межі та обмеження

- У скоупі: тека module1/practice/ (README, бекенд, запуск, тести); ланцюжок find_shipments -> деталі;
  вузька перевірка сум; бюджетний ліміт на межі прогонів; тести з підміненою моделлю; 5 реальних прогонів.
- Поза скоупом: будь-які зміни курсових файлів (core/, domain/, modules/, config.py, run.py, demo.py);
  CAPABILITIES і BASIC незмінні; create_claim і будь-яка мутація стану — до модуля 4; челенджі A і B —
  окремими рішеннями пізніше; нові залежності — жодних (раннер — `unittest` зі стандартної бібліотеки).
- Обсяг за карткою: Основа повністю + челендж C (тест без мережі + бюджет).
- Домен: поштовий, у власному бекенді практики (копія структури ORDERS зі своїми даними), курсові
  інструменти не перевикористовуються.

## Зауваження, що вціліли

- [підтверджено] run_agent жорстко імпортує dispatch з domain.backend — власні інструменти маршрутизуються
  через domain.backend.IMPL.update(PRACTICE_IMPL) у точці входу практики, не побічний ефект імпорту; перед
  update — голосна перевірка перетину імен через `raise`, бо колізія мовчки затіняє курсову реалізацію
  (доведено прогоном) (критик, архітектор, прагматист)
- [підтверджено] Бюджетна зупинка можлива лише на межі прогонів: on_step не придатний (виняток з нього
  прошиває run_agent без результату — доведено прогоном), core правити заборонено. Гранулярність — один
  прогін; README формулює стелю чесно, без формули MAX_TURNS x MAX_TOKENS (input-токени нею не обмежені)
  (критик, перформансник, архітектор)
- [підтверджено] Перевірка сум: грошові числа у відповіді мусять бути присутні у виходах інструментів (trace);
  ідентифікатори не перевіряються; обмеження (суми словами, формати з комою) названі в README як межа
  (безпека, прагматист — зійшлися після допиту)
- [підтверджено] Ворожий прогін із підкинутою сумою в запиті («мені належить 5000 грн») — обов'язковий
  кейс серед прогонів (безпека)
- [підтверджено] Телефон зводиться до канонічного вигляду ДО пошуку, і у відповідь іде лише він. Сирий
  текст клієнта назад не потрапляє: усе, що повертає бекенд, модель читає як підтверджений системою
  факт, тож інакше клієнт дописував би собі факти чужими руками (безпека)
- [підтверджено] Бекенд практики ніколи не кидає винятків — лише повертає {"error": ...}: dispatch ловить
  тільки TypeError, усе інше прошило б цикл наскрізь (безпека, критик)
- [підтверджено] raise SystemExit на старті практики, якщо config.MODEL відсутній у PRICES (не assert:
  python -O вирізає assert-и), інакше бюджет рахує вартість у нуль і не спрацює ніколи (критик)
- [підтверджено] Мок _call лишає USAGE нульовим (доведено прогоном), тому тест бюджету — окремий юніт на
  синтетичному USAGE; тест ланцюжка — на моку _call; тест ізоляції — після реєстрації tools_for(1)
  повертає ту саму одну схему, CAPABILITIES незмінний, імена не перетинаються (критик, архітектор)
- [підтверджено] Для tool_error-прогону в даних бекенду засівається зламаний запис: пошук його знаходить,
  деталі по ньому повертають помилку (критик)
- [підтверджено] Запуск: python -m practice.run з теки module1/ (інакше practice/ не побачить config і
  core); команда і точка входу записані в README дослівно; тести ставлять фіктивний ANTHROPIC_API_KEY до
  імпорту, жодних літералів, схожих на ключ (критик, безпека)
- [підтверджено] Рівно два інструменти у схемах (кожен зайвий — це вхідні токени схем у кожному виклику);
  команди чотирьох зламаних прогонів — однорядкові, готові до копіювання; api_error демонструється зіпсованим ключем
  (падає з першої спроби, без ретраїв); демонстрація бюджету — ліміт нижче вартості одного прогону,
  відмова до першого виклику, нуль витрат (перформансник)
- [підтверджено] П'ять станів приймаються у фактичній формі контракту ядра: outcome (ok, turns_exhausted,
  api_error) + failures (tool_error) + прапорець no_tool_used; бюджетна відмова — стан обгортки практики,
  не шостий outcome (архітектор)

## Позначене допитувачем

- [суперечить безпеці] «зрізати grounded() повністю» (прагматист) проти «полагодити» (безпека) —
  розв'язано синтезом, обидва погодились: широкий grounded() зрізано, вузька перевірка сум лишається,
  плюс ворожий прогін. Рішення користувача: прийняв синтез.
- [слабке] «IMPL.update безпечний, бо агент викликає лише інструменти зі свого списку» (архітектор) —
  замінено трьома гарантіями: реєстрація тільки в точці входу, перевірка перетину імен, успадкована модель
  загроз (IMPL вже сьогодні ширший за BASIC). Контрольний прогін run.py знято самим архетипом як театр.
- [слабке] «перевірка перед кожним викликом» (перформансник) — знято автором після підрахунку: різниця до
  ~$0.11 у патологічному випадку не варта підміни _call під час роботи.
- [слабке] «новий домен дешевший» (прагматист) — визнано помилкою формулювання: заперечення стосувалося
  курсових інструментів, а не доменної моделі.

## Свідомо не робимо

- grounded() загального призначення (перевірка ідентифікаторів, дат, довільних чисел) — ловить строго
  менше, ніж читач прогону; матеріал модуля курсу про оцінювання.
- Зупинка бюджету всередині прогону — вимагала б правки core/agent.py або підміни під час роботи.
- Параметр dispatch у run_agent — чесніше архітектурно, але це зміна core без другого споживача.
- Челенджі A і B зараз; create_claim, підтвердження людиною, ідемпотентність — до модуля 4.
- pytest — нова залежність без потреби, requirements.txt лишається дворядковим.

- Доступність speckit: не підключений; користувач обрав не підключати.
- Рішення користувача: direct-verified затверджено 2026-08-19; раннер — `unittest` зі стандартної
  бібліотеки; впровадження НЕ починається до окремої команди користувача.
- Додаткові вимоги користувача (2026-08-19): максимальна документація впровадження (мова довільна —
  українська або англійська): README практики пояснює не лише як запускати, а і як влаштовано кожне
  рішення; докстринги в кожному файлі практики в стилі курсу; після завершення — звіт відповідності
  чеклістам картки (Основа + челендж C), пункт за пунктом, з доказом по кожному чекбоксу (файл, тест
  або прогін); пункти поза скоупом (A, B, D) у звіті позначаються явно, а не пропускаються.
- Список перевірок:
  - безкоштовне збирання: python -c "import practice.run, practice.backend" з module1/ проходить;
  - unittest без мережі і без .env (фіктивний ключ через змінну оточення): юніт бюджету на
    синтетичному USAGE, тест
    ланцюжка на моку _call (аргумент другого інструмента походить з виходу першого), тест реєстрації
    (перетин імен падає голосно), тест ізоляції (tools_for(1) і CAPABILITIES незмінні після реєстрації),
    тест контракту бекенду (not_found замість винятку, нормалізація телефону), тест чекера сум;
  - регресійна перевірка челенджа C: навмисно зламати обробку помилки — тест мусить впасти;
  - 5 реальних прогонів (запускає користувач): щасливий ланцюжок; api_error (зіпсований ключ);
    turns_exhausted (MAX_TURNS=1 через env); tool_error (засіяний зламаний запис); ворожий запит із
    підкинутою сумою; вивід дослівно в README практики;
  - перевірка, що жоден курсовий файл не змінено: git status показує лише нові файли під
    module1/practice/ і docs/.
