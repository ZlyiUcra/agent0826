# Агент-довідник специфікації ECMAScript

Питання на кшталт «чому `NaN !== NaN`» чи «що робить `Array.prototype.at` із від'ємним індексом» мають точну
відповідь у специфікації ECMA-262, але сама специфікація — сотні сторінок алгоритмічного тексту, і шукати в
ній руками довго. Цьому агентові питання ставлять звичайною мовою: він сам вирішує, що шукати в тексті
специфікацій, за потреби дочитує знайдені розділи повністю і відповідає стисло — з номером розділу, на який
можна послатися в код-рев'ю чи багрепорті.

Для користувача це одна команда: питання на вході — відповідь із посиланням на розділ на виході. Скільки
кроків пошуку зробити, які розділи дочитати і коли зупинитися — агент вирішує сам, у межах ліміту кроків.

## Швидкий старт

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env                                 # впишіть свій ключ Anthropic

.venv/bin/python -m practice.base.agent --tools      # $0: перевірка з'єднання з сервером знань
.venv/bin/python -m practice.base.agent "Чому NaN !== NaN?"   # платний прогін
```

Запускати з кореня цієї теки: код імпортує `config`, `core` і `practice` як пакети верхнього рівня.

## Чому `NaN !== NaN`

Оператор `===` реалізований через абстрактну операцію **`IsStrictlyEqual`** (розділ **7.2.14**). Якщо обидва операнди є числами, вона делегує порівняння операції **`Number::equal`** (розділ **6.1.6.1.13**).

А `Number::equal` визначена так:

> 1. Якщо `x` є `NaN` — повернути **false**.
> 2. Якщо `y` є `NaN` — повернути **false**.
> 3. Якщо `x` є `y` — повернути **true**.
> …

Тобто, щойно будь-який з операндів є `NaN`, операція негайно повертає `false` — незалежно від другого операнда. Саме тому `NaN === NaN` дає `false`.

---

**Звідки це правило?** Воно прийшло зі стандарту IEEE 754 для чисел з рухомою крапкою, якому ECMAScript слідує для типу Number. `NaN` означає «не число» і є результатом невизначених операцій (наприклад, `0/0`, `Math.sqrt(-1)`). Оскільки таких «невизначених результатів» може бути нескінченно багато, вважається, що два значення `NaN` не можна вважати рівними.

---

**Як перевірити `NaN` правильно?**

```js
Number.isNaN(x)   // розділ 21.1.2.4 — повертає true лише для NaN
```

Або скористатись `Object.is(NaN, NaN)`, який використовує `SameValue` (розділ **7.2.9**) — та операція, навпаки, вважає `NaN === NaN` істиною.

## Reflect vs Object: у чому різниця?

### Ключова різниця між `Reflect.defineProperty` і `Object.defineProperty`

Специфікація (розділи **28.1.3** і **20.1.2.4**) дає точну відповідь через порівняння кроків двох функцій.

**`Object.defineProperty`** (розділ 20.1.2.4):
1. Якщо `obj` не Object — кинути `TypeError`.
2. `propertyKey = ToPropertyKey(key)`
3. `propertyDesc = ToPropertyDescriptor(attrs)`
4. Виконати **`DefinePropertyOrThrow`** → якщо операція не вдалась — **кидає виняток**.
5. **Повернути сам об'єкт `obj`**.

**`Reflect.defineProperty`** (розділ 28.1.3):
1. Якщо `target` не Object — кинути `TypeError`.
2. `propertyKey = ToPropertyKey(key)`
3. `propertyDesc = ToPropertyDescriptor(attrs)`
4. **Повернути результат `target.[[DefineOwnProperty]](propertyKey, propertyDesc)`** — тобто **`true` або `false`**.

---

### Підсумок відмінностей

| | `Object.defineProperty` | `Reflect.defineProperty` |
|---|---|---|
| **При невдачі** | Кидає `TypeError` | Повертає `false` |
| **При успіху** | Повертає сам об'єкт | Повертає `true` |
| **Стиль** | Виключення як потік керування | Булева відповідь |

---

### Навіщо взагалі потрібен `Reflect`?

Три головні причини:

1. **Відповідність внутрішнім методам об'єкта (`[[...]]`).** Кожен метод `Reflect` — це пряме відображення одного внутрішнього методу: `Reflect.defineProperty` → `[[DefineOwnProperty]]`, `Reflect.get` → `[[Get]]` тощо. `Object.*` так не влаштований.

2. **Зручна робота з `Proxy`.** Трапи `Proxy` (розділ 10.5) мають ті самі назви, що й методи `Reflect`. Всередині трапу можна просто викликати відповідний `Reflect`-метод, щоб делегувати поведінку далі без зайвого коду. Це й була головна мотивація дизайну.

3. **Передбачуваний тип значення, що повертається.** `Reflect`-методи повертають `Boolean` (успіх/невдача) замість того, щоб кидати виняток — це дозволяє писати умовну логіку без `try/catch`.

**Приклад у `Proxy`:**
```js
const proxy = new Proxy(target, {
  defineProperty(target, key, desc) {
    console.log('intercepted');
    return Reflect.defineProperty(target, key, desc); // повертає true/false
  }
});
```

Якщо б тут використовувався `Object.defineProperty`, довелось би вловлювати виняток і вручну перетворювати його на `Boolean`.

## Порядок ключів у `Object.keys`

`Object.keys` визначено в розділі **20.1.2.22**. Там написано, що функція викликає абстрактну операцію **`EnumerableOwnProperties(obj, key)`** (розділ **7.3.23**), яка своєю чергою отримує список ключів через внутрішній метод **`[[OwnPropertyKeys]]()`** об'єкта.

Порядок, у якому `[[OwnPropertyKeys]]` повертає ключі, визначено в розділі **10.1.11.1 `OrdinaryOwnPropertyKeys`** і є таким (три групи, строго по черзі):

1. **Цілочислові індекси** (array indices) — у **зростаючому числовому порядку** (ascending numeric order).
   Наприклад: `"0"`, `"1"`, `"2"`, …

2. **Рядкові ключі, що не є індексами** — у **хронологічному порядку створення** (ascending chronological order of property creation).
   Наприклад: `"foo"`, `"bar"`, `"baz"`, …

3. **Symbol-ключі** — у хронологічному порядку створення.
   *(але `Object.keys` їх не повертає, бо `EnumerableOwnProperties` пропускає не-рядкові ключі)*

---

### Приклад

```js
const obj = { b: 1, 2: 2, a: 3, 0: 4, 1: 5 };
Object.keys(obj);
// → ["0", "1", "2", "b", "a"]
//      ↑ індекси за зростанням  ↑  рядки в порядку створення
```

---

**Підсумок:** порядок ключів у `Object.keys` — не довільний і не "порядок вставки" у чистому вигляді. Спочатку йдуть числові індекси за зростанням, потім решта рядкових ключів у порядку їхнього додавання до об'єкта. Це гарантується специфікацією через ланцюжок: `Object.keys` → `EnumerableOwnProperties` (§7.3.23) → `[[OwnPropertyKeys]]` → `OrdinaryOwnPropertyKeys` (§10.1.11.1).

## Що всередині

Агент — це цикл ухвалення рішень над моделлю Claude. Текст специфікації в саму модель не вшитий: усе, що вона
знає, — це питання користувача і результати власних пошуків. На кожному кроці вона або викликає інструмент
пошуку, або, зібравши досить контексту, пише відповідь. Знання живуть окремо — у
сервері знань, під'єднаному через MCP по stdio, з двома інструментами: `search_spec` (пошук фрагментів за
запитом) і `read_section` (повний текст розділу за id з видачі пошуку). Навколо циклу стоять чотири шари
захисту: фільтр вхідного запиту, правила перед кожним викликом інструмента, список дозволених інструментів і
фільтр готової відповіді з перевіркою окремою дешевою моделлю.

- `practice/base/agent.py` — агент: цикл, виклики моделі, диспетчер інструментів;
- `practice/base/spec_server.py` — сервер знань: індекс специфікацій і два інструменти через MCP;
- `practice/base/layers.py` — чотири шари захисту навколо агента;
- `practice/base/setup.py` — підготовка пошуку (за бажанням — вектори, див. нижче);
- `practice/common/` — корпус, пошук по словах, режим пошуку;
- `practice/docs-full/`, `practice/docs-suite/` — тексти ECMA-262, ECMA-402, ECMA-404 і ECMA-414: 72 файли,
  з яких сервер знань індексує 4168 фрагментів із 71 розділу;
- `config.py`, `core/agent.py` — ключ і моделі з `.env`, клієнт API з ретраями та обліком токенів.

## Пошук: по словах чи за змістом

За замовчуванням сервер знань шукає по словах (BM25) — це не потребує жодних додаткових пакетів і сервісів.
За бажанням пошук перемикається на вектори: `python -m practice.base.setup --vectors` піднімає Qdrant у
Docker, рахує вектори фрагментів (пакет `fastembed`) і перемикає режим; `--words` повертає назад. Для
демонстрації агента вистачає пошуку по словах.

Платний лише повний прогін: цикл агента працює на `claude-sonnet-4-6`, перевірка відповіді — на дешевій
